## Established execution boundaries

The current automatic builder calls HaulChurnGuard.NoteBulkAnchor after constructing its candidate (`BulkHaul.cs`). Candidate construction, including a real scanner call during an active approach, is not physical transport. The existing legacy dictionary records only Thing ID, tick and source count. The actual B1 query scenes now demonstrate its resulting false recurrence without any executed haul.

Actual bulk pickup occurs in JobDriver_BulkHaul's take toil: after live forbiddance/storage/foreign-retarget/capacity gates, it calls source.SplitOff(count) and DepositSwept. Full-stack SplitOff can return the original object; a partial split creates another object. DepositSwept can directly absorb the split into one or more already tagged inventory stacks, destroy a fully absorbed input and tag actual growth on the absorber. The original source Job target or a successful Boolean alone cannot identify all resulting cargo.

Delivery is a separate JobDriver_UnloadHauledInventory job. It transfers tagged inventory into hands, invokes actual native cell/container placement, or takes explicit fallback paths. A successful unload end can also mean that no remaining item can be unloaded; it is not proof all cargo reached useful storage. Notify_PatherFailed can put carried cargo back in inventory, tag and skip it, then continue or finish successfully. The physical outcome must therefore be tracked across both jobs and their actual terminal cleanup. Internal unload scheduling can say forced=True in debug output while the actual job.playerForced remains false; do not confuse it with a player's forced order.

Existing failed-placement/failed-job budgets and the separately evidenced foreign path-retarget protection remain required. The successful-loop repair must not disable those mechanisms or infer foreign causation from an unproductive result.

## Proposed observation contract

Use an execution-only pickup frame around the real split/deposit operation, entered only while the exact automatic bulk Job and driver are current on that pawn. Capture source map/cell/Thing identity and quantity before the operation. Commit an attempt only after verified quantity leaves that source and enters the actual pawn's cargo. A reservation, current job, attempted split, zero transfer or pre-pickup cancellation creates no completed attempt.

Represent an attempt separately from a Job: pin pickup Job object/loadID and pawn, source context, actual picked quantity, current attributable descendants and an outcome state. The bulk job ending successfully must not resolve the attempt while its cargo is still held for a later unload. The eventual unload may deliver several origins together, so each attempt needs its own quantity outcome.

The minimal outcomes are useful delivery, verified return to source, unresolved/held, and attribution unknown. Count a completed zero-progress return at most once. Actual delivery away from the original context, shrinking remaining work and partial delivery are progress, not accumulated failures. If only part of the original quantity returns, do not describe a whole-quantity net-zero loop. Interrupted unresolved cargo cannot be converted into a completed return by cleanup alone.

A second kind of recurrence requires an explicit decision: HD can successfully deliver A to B and an external operation can subsequently return the same cargo to A. Observing the next candidate is insufficient. A later verified pickup of attributable returned cargo could close the prior A-to-B-to-A cycle, but only with evidence of the earlier actual delivery, quantity continuity and return context. This is distinct from HD itself placing the cargo back at A. Neither case identifies which mod caused the return. An implementation must cover the requested repeated successful-return scenario without counting ordinary newly generated or replenished resources at the same cell as old cargo.

## Lineage and custody questions requiring independent investigation

Driver-local source/result snapshots cover uncomplicated full/partial pickup and direct inventory merges, but later native placement and foreign operations can split or merge the same cargo again. Whole-Thing tags and the legacy Thing-ID dictionary are insufficient. A focused investigator must recommend a bounded tracking design after reading the actual native split/absorb/transfer/drop execution order and the applicable HD/CE paths.

Candidate approaches are narrowly instrumented native split/absorb hooks for already tracked cargo, or explicit transfer scopes covering every required operation with a conservative unknown state when an unobserved transformation occurs. Hook registration alone is not coverage: custom virtual overrides and transformations outside HD's stack can bypass a base-method hook. Any unsupported lineage route stays explicit instead of silently treating a destroyed input as delivered or resetting the loop into invisibility.

Fungible merged quantities need a defensible attribution rule. Assigning arbitrary unit labels in a test is not independent proof that a particular origin supplied a later partial split. The product may track exact cohorts where all descendants are observed and use conservative bounds or an unknown outcome for ambiguous partial redistribution. Independent review must decide which outcomes remain provable and supply discriminating merge/split controls. It must not approve a rule solely because it matches the fixture's chosen labels.

Bound retained state by explicit maximums and lifetime; publish an unknown/expired diagnostic state when necessary rather than inventing a return. Simulation writes must remain deterministic; worker-thread queries must not mutate recurrence state. Source identity includes map and location; cross-map movements, changed cells, pawn overlap and recycled Job identities must not combine unrelated work. Load hygiene clears session-only observations through the existing CacheRegistry path. A resumed save must neither inherit an unrelated completed count nor manufacture success from missing history; persistence behavior requires its own runtime check.

## Causal return history contract

Independent addendum `%TEMP%/haulersdream-executed-attempt-episode-api.md`, SHA 14B8132F4E73A98C3288D3828502B4940E08F8A8ED06701AE7771DC22CE16055, separates physical OriginLot, source-specific ReturnEpisode and actual PickupAttempt. A return at depth k+1 requires a qualifying depth-k predecessor already completed before that attempt's immutable pickup boundary. Operation sequence, not only tick equality, orders this relation. Six parallel initial pickups followed by six returns yield six depth-one quantities, never a depth-six shared counter. An attempted pickup or a scanner query creates no return certificate.

Freeze the predecessor profile at actual pickup. A returned portion picked up before its parent attempt closes cannot later inherit the parent's completion retroactively. Retain separate quantity-qualified history classes after mixed-depth merges; full closed-mixture return can recover origin certainty without summing serial depths. Only a lower bound covering all offered cargo establishes that the whole offered quantity meets a recurrence threshold. Partly implicated mixed cargo remains explicit and cannot justify suppressing unrelated units. Useful delivery followed by an observed external return is a distinct causal path; fresh replacement resources remain a new episode.

The next owning model must enforce same-origin/session identity and non-overlapping live fragment membership, atomic parent retirement/output registration, conserved live and terminal/sink budgets, and physical capacity across all origin bounds. Independent arithmetic review demonstrates that global totals plus individual intervals can lose subgroup constraints after split/remerge. Retain bounded transformation constraints for subgroup claims, or return unresolved when the available bounds cannot prove the claim; never turn lost precision into invented FIFO/LIFO identities or an exact-empty success. An interval model's consistency alone is not a certificate of full joint feasibility. Overflow, stale versions, duplicate receipt envelopes, unknown transformations and exceeded limits require atomic rejection/invalidation with explicit diagnostics. These are pending model requirements, not established behavior of CargoOriginBounds.
