## Confirmed cause and recurrence

HD's `Patch_BillRepeatModeUtility_MakeConfigFloatMenu.Prefix` runs at Harmony priority 800, builds a replacement menu, and returns false. It restores only Everybody Gets One, Compositable Loadouts, and Ingredient Threshold entries. Periodic Bills' actual `Patch_FloatMenu.Prefix` is another bool-returning full replacement at the default priority 400. Consequently HD runs first and skips Periodic Bills' menu prefix. Swapping load order does not override that priority difference. This is a missing menu entry, not evidence that the periodic Def or saved schedule was overwritten.

Both published and retained pre-change candidate HD menu methods have identical inspected IL instructions and patch attributes. At the diagnosis checkpoint, the inspected menu, button-label, and batch-planner sources also matched the v1.24.0 tag after line-ending normalization. F45 is still present in those compiled images; the source implementation recorded below has not been built. The diagnosis is source/assembly evidence; a retained native failure demonstration has not yet been executed.

Harmony specifically skips later prefixes with side effects after a false-returning prefix; side-effect-free void prefixes, postfixes, and finalizers have different behavior. The existing HD comments claiming *every* remaining prefix is skipped are too broad and should be corrected during this work. [Harmony prefix behavior](https://harmony.pardeike.net/v2/articles/patching-prefix.html), [priority rules](https://harmony.pardeike.net/v2/articles/priorities.html).

This is a **recurring architectural omission across different integrations**, with no evidence that Periodic Bills itself was previously fixed:

## Behavior that must coexist

Periodic Bills owns a real custom repeat Def, `PeriodicBills.PeriodicBillDefOf.PB_Periodic`. Its selection delegate assigns that Def. Its own game component stores the amount, interval, produced count, and last completion tick. The actual DLL counts **recipe iterations**, not individual yielded products. A recipe producing four items per iteration therefore yields eight items for two configured iterations. Its own UI exposes that yield distinction. The next interval is measured from cycle completion; the first cycle is immediately eligible. HD must preserve these semantics rather than inventing a second timer or translating the mode into vanilla `RepeatCount`.

HD already refuses to batch a custom repeat mode in `CraftBatchPlanner.CanBatch`. Its batch row marker and button prefix use the same availability gate. Preserve those rules: a periodic bill must not display an active HD batch marker or run `HaulersDream_BatchCraft`. Ordinary inventory ingredient gathering may still precede the native bill driver, but must respect the real `ShouldDoNow` decision and produce exactly one completion notification per actual iteration.

Selecting periodic mode after a batch bill must leave the bill in an unambiguous non-batch state. Selecting an HD batch option must deliberately choose the corresponding supported vanilla mode. A failed/rejected selection must not silently disable batching or erase the periodic configuration. Existing periodic saves, settings, suspension, and remaining cooldown must remain meaningful.

## Design comparison and recommendation

**Recommend bounded cooperative menu augmentation, with explicit selection semantics and retained support for the existing integrations. Do not finish this item by merely adding a fourth unconditional reconstruction bridge.** The evidence supports removing HD's own exclusive-menu behavior; it does not support an unrestricted global menu merger.

The native lifecycle was inspected directly:

1. `MakeConfigFloatMenu(Bill_Production)` returns void and creates a local option list, constructs one `FloatMenu`, then passes it to `WindowStack.Add`.
2. `FloatMenu(List<FloatMenuOption>)` copies and sorts the list by priority/order, applies each option's size mode, and plays the menu-open sound.
3. `WindowStack.Add` removes an existing window of the same type, assigns an ID, calls `PreOpen`, inserts/focuses the window, then calls `PostOpen`. Initial sizing/positioning depends on the actual option list.
4. The menu has a protected option list but no bill identity or public typed repeat-mode metadata. An arbitrary option is a label plus an action and other presentation/interaction state, not a `BillRepeatModeDef` entry.

| Approach | Assessment |
|---|---|
| Add `PeriodicBillsCompat.TryInsertModes` to HD's replacement | The smallest exact fix is possible: resolve the real Def and reproduce PB's simple selection. It preserves current known bridges, but repeats the omission model from three earlier fixes. Suitable as a diagnostic comparison, not the recommended final architecture. |
| Postfix the method and replace/modify the last open menu | Reject. The method returns no menu identity, window opening already performed sizing/callbacks, and replacing it can repeat sounds or remove the wrong menu. Merely extending the private list after opening can leave incorrect dimensions/size modes. |
| Transpile only the native body to insert HD entries | Insufficient. PB and Ingredient Threshold can skip that body, so HD's entries disappear. |
| Append HD controls while the actual menu is being constructed, within the exact bill-menu call | Recommended bounded basis. Preserve original option objects, actions, guards, tooltips, disabled states and ordering; append HD's own options before native sorting/sizing. A small scoped constructor hook is feasible for the inspected native and PB paths, both of which construct one menu synchronously. |

Implementation requirements for the recommended approach:

- Replace HD's false-returning prefix with a scope that lets the original/other mod run. Capture the exact bill, use a reentrant per-thread stack, and clean up in an exception-preserving finalizer. Establish ordering against the **actual** supported menu creators. No process-global “current bill”, no context surviving the call, and no inference from whichever menu happens to be open.
- Intercept the concrete `FloatMenu(List<FloatMenuOption>)` construction only while that scope is active. Work with a fresh list containing the original option objects plus HD additions, so the native constructor still performs sorting, size assignment and its single sound. Do not create or reopen a second menu. Unrelated menus outside the scope remain unchanged. Nested, exceptional, zero-menu and multiple-menu paths need discriminating controls before this hook is accepted.
- Keep provider actions authoritative, with the adopted narrow correction of IT's inadequate proxies above. HD must not itself enumerate all loaded repeat Defs and blindly assign them: other mods can require recipe guards and extra per-bill setup. Do not run an option merely to discover its mode. Do not deduplicate by translated label.
- Handle selection transitions explicitly. A blanket wrapper that clears HD's flag after every foreign action is wrong: native TargetCount can return normally after rejecting a recipe, and an extension could add a settings action. Conversely, clearing only when `repeatMode` changes misses reselecting the plain version of the currently batched vanilla mode. Resolve those cases with bounded, source-verified action/provider metadata; preserve unknown actions. This is a required design/QA gate, not permission to ship ambiguous flag behavior.
- Removing HD's takeover does not make **two other full-replacement mods** cooperate. PB can still suppress Ingredient Threshold, and either can skip EGO/CL transpilers. Preserve HD's existing support with narrowly identified provider contributions when their original contribution did not run. Presence/duplication checks must use actual provider/action provenance, not label guesses. Confirm the concrete loaded versions of EGO/CL/IT before implementing this part; the current HD bridge comments alone are insufficient acceptance evidence.
- Prove with an additional synthetic foreign mode that HD retains a previously unknown original option and invokes its original action once. That specifically distinguishes removing this architectural cause from another four-mod allowlist. Do not promise compatibility with every hypothetical menu replacement or higher-priority patch.
- Continue to use the existing synchronized mutation path for HD's saved state. Do not assume that PB's arbitrary UI actions or fields are multiplayer-safe merely because native `bill.repeatMode` is supported. Verify the requested HD behavior in the supported multiplayer configuration or retain an explicit evidence-backed limitation.

The focused independent design review above is complete and its concrete action/proxy decisions govern implementation. Source and compiled QA must verify the actual implementation of those decisions. If implementation or runtime evidence proves scoped composition unsafe for an actual supported creator, revise the design with evidence; do not silently revert to the old replacement model and label the recurrence solved.

## Source implementation checkpoint — 20 September 2026

The authored source replaces HD's false-returning menu prefix with a First/before-PB-and-IT scope prefix and an exception-preserving finalizer. `BillRepeatMenuComposition` uses a per-thread frame chain and recognizes a menu only through a known action capturing that frame's exact bill. It creates a fresh list before the real FloatMenu constructor sorts/sizes it; no menu is opened or replaced by HD. Unrelated lists are retained, nested calls have separate bill identities, and both returned-list and HD option identity prevent repeated additions within a frame.

`BillRepeatMenuProviders` reads the registered native-menu patch inventory on the first real menu call, checks supported patch owners/types and their active loaded assembly ownership, and resolves only the five known factories/Def contracts. It follows their action references, validates the 3 native + 4 PB + 3 EGO + 1 CL + 1 IT action shapes, and retains their original delegate identities. It neither scans all assemblies for assignments nor matches translated labels. The legacy menu bridge entry points now use this catalogue; an early IsActive query does not initialize it during mod startup. CL's separate inventory keep behavior is retained.

The composer retains adequate original contributions, calls EGO/CL's actual factories once when needed, and replaces only IT's identified inadequate TargetCount/EGO/CL proxies. IT's adequate PB/IT/simple native entries and unknown contributions survive. Missing PB/IT contributions use their source-verified simple Def assignment. Weak option-identity records recognize HD-owned plain fallback actions without inspecting arbitrary closures or replacing unknown delegates. A binding/composition failure is logged and preserves the original menu instead of restoring an exclusive takeover.

`BillRepeatMenuActions` adds an accepted marker around the actual mode store in each known action and checks that marker at normal returns, after CL's setup writes. Same-mode plain selections clear batching; rejected branches do not. It preserves original delegates and executes each original guard/store once. The normal-return guard preserves incoming return labels and rejects unsupported multiple-store/exception-region/prefixed-write shapes rather than guessing. HD batch/size/overshoot actions retain their existing behavior and custom-mode availability gate.

The small `MultiplayerCompat.CompletePlainBillSelection` helper preserves the existing SetBillBatch UI route and writes directly only when already replaying an MP command through the existing optional API boundary. No other nearby/drop/refuel command logic was changed by this item. This is source intent, not proof that a foreign provider or fallback action is synchronized; the existing MP acceptance requirement remains open.

The concise patch changeset is `.changeset/cooperative-bill-modes.md`. No new player-visible translation keys are needed.
