# L04-O1 storage ownership adapter fixture

Implementation: `tools/RuntimeHarness/StorageOwnershipScenario.cs`. This is a non-shipped harness file, called as `StorageOwnershipScenario.Run(map, expectedBehavior)` after the isolated game has initialized a real player-home map. The root runner must attach the returned `StorageOwnershipResult` to its durable run result and preserve the existing loaded-assembly hashes, startup/error checks, and protected-player-file verification.

This document describes an implemented fixture, **not recorded runtime success**. The fixture author has not built or launched it. Root owns compilation, independent review, baseline execution, and corrected execution.

The witness addresses the concrete production custody adapter defect found during L04 investigation. The installed RimWorld 1.6.4871 assembly exposes `Thing.holdingOwner` as a `ThingOwner`, while `Thing.ParentHolder` returns `holdingOwner?.Owner`. A pawn inventory's owner is its `Pawn_InventoryTracker`. Comparing `ParentHolder` against the inventory's `innerContainer` therefore fails for real inventory cargo. The fixture resolves and invokes the loaded HD assembly's private `IsDelivering`, five-argument `FreeUnitsFor`, `TryCommit`, `UnitsMovingOf`, and `ClaimedByOthersFor`; it never supplies a synthetic delivery Boolean to Core.

Each control uses a fresh real pawn and a separate actual one-cell `Zone_Stockpile`, registered with the map's `ZoneManager`. The stockpile accepts Steel at Critical priority. A compatible Steel stack occupies all but 10 units of capacity, or 14 for the competing-claim control. Preconditions measure capacity using the actual `GetItemStackSpaceLeftFor`, production `FreeUnitsFor`, and patched `StoreUtility.IsGoodStoreCell` before that group's claims exist. Unique actors and groups prevent one control's same-tick memo from serving another control. Every claim is created through production `TryCommit` and must have an equal quantity reported by production `UnitsMovingOf` after the claim write invalidates the evidence memo.

| Control | Live evidence and subject | Corrected IsDelivering / FreeUnitsFor | Baseline IsDelivering / FreeUnitsFor |
|---|---|---|---|
| Own inventory | 10 units in the asking pawn's actual inventory, registered by `CompHauledToInventory.RegisterHauledItem`; own claim 10 | true / 10 | false / 0 |
| Own hands | Actual carry tracker holds 10; fixture current vanilla `HaulToCell` job names that cargo/destination; own claim 10 | true / 10 | true / 10 |
| Other pawn inventory | Subject is actually held/tagged by a distinct pawn; its claim occupies all 10 spare units | false / 0 | false / 0 |
| Floor with own in-flight claim | Subject is a separate spawned floor stack; asking pawn holds another tagged 10 units with a live claim | false / 0 | false / 0 |
| Own inventory plus another live claim | Asking pawn holds/claims 10, another pawn holds/claims 4, stockpile has 14 free; `ClaimedByOthersFor` must return 4 | true / 10 | false / 0 |
| Missing inventory | Temporarily null inventory tracker on the disposable actor, with an unheld subject and no own claim | false / 10 | false / 10 |
| Hands with missing inventory | Actual hand cargo and vanilla haul job provide 10 live claim units despite a temporarily null inventory tracker | true / 10 | true / 10 |
| Null pawn, null subject, both null | Explicit invalid adapter inputs | false / int.MaxValue | false / int.MaxValue |

For every non-null subject control, the actual Harmony-patched `StoreUtility.IsGoodStoreCell` must agree with whether the expected free quantity is positive. Null controls avoid calling that API outside its Thing contract. The file records custody reference equality, owner types, current tick, loaded production assembly identity/MVID, exact observed adapter answers, and separate baseline/corrected expectations. Fixture assertions and requested-behavior assertions are distinguished in structured output. Caught exceptions produce an explicit inconclusive result and failed fixture assertion; failure does not depend on a thrown exception escaping Verse.

`expectedBehavior` accepts `baseline-gap` or `satisfied`. The former matches only when **every** baseline row matches and requested behavior is still unsatisfied. It produces `behavior-gap-observed` with `requestedBehaviorSatisfied=false`. The latter requires **every** corrected row. A fixture precondition failure is inconclusive. These statuses must remain distinct when integrating with the runner; an expected old failure is never a passed feedback item.

The fixture is synchronous and asserts that no game tick advanced. The hand controls install a real vanilla Job object as explicit adapter input; they do not call `StartJob`, create a job driver, or execute toils. All fabricated current-job inputs are cleared in `finally`, all claims created by this fixture are retired through production `Commit(..., 0, ...)`, and temporarily missing inventory trackers are restored in their own `finally` blocks. Generated initial actors/landing objects are despawned on this disposable map, and newly generated fixture pawns have work disabled.

This is strong runtime evidence for the ownership adapter and its actual storage gate consequence. It does **not** establish automatic bulk pickup/unload completion, reservation coexistence over executed ticks, storage-loop convergence, the original reporter's mod combination, save/load, or multiplayer. The plan's full L04-O1 row still requires an independently observed automatic bulk pickup into inventory followed by delivery to available reserved higher-priority storage. That later lifecycle test should be separate so a successful adapter witness cannot be mistaken for complete gameplay coverage.
