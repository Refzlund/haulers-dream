## Chosen design and alternatives

The current prep job keeps only floor selections, gathers, ends, and relies on a new work scan to choose a recipe plan. That loses the original quantity contract. The broad mixing and any-tagged-stock guards contain symptoms without proving a complete recipe handoff.

The reviewed design selected option 1, using a new fixed-layout driver/def while preserving the legacy prep. Option 2 remains the considered alternative with save-layout and CS iterator-composition costs. See the design review for the actual native API constraints and handoff rules.

1. Retain and remap the original native bill selection through a separate prep job, with a single successful native `DoBill` continuation. All nine safeguards in the investigation apply, particularly actual transfer provenance, player-order precedence, reservation boundaries and scribed ownership. `Job.Clone()` aliases mutable queues and is not an independent plan.
2. Gather inside the native `DoBill` lifecycle before its collection toils. This retains recipe/job ownership and reservations but must compose with CS's replacement iterator, stable saved toil indices, legacy active jobs, off controls and HD's ingredient-relocation deference. Adding toils conditionally based on changed inventory at reload is not a safe persistence design.

The runtime witness should discriminate before/after behavior independently of either architecture. Keep the original bill's repeat mode and native consumption/recipe hooks. A chosen architecture must explain why the earlier loop cannot recur through reselection, not merely report that a warning stopped appearing.
