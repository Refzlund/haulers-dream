# Native source boundary and control-specific acknowledgement

The fresh v11 result has a positive control witness and a failed observation witness: events78/79 record the actual gear `ButtonImage` result and the real product action; event80 times out waiting for acknowledgement. Neither a worker PostMessage receipt alone nor a late Used event is treated as proof of a particular actionable native event. This revision observes the actual execution branch before consumption.

The native `Window.WindowOnGUI` calls `GUI.Window` with `InnerWindowOnGUI`. Control-local GUI event context can therefore differ from the earlier outer Root/play observation. The observed Used values do not establish the precise internal Unity consumption order, and this correction does not require such an inference. The actual positive native control path is sufficient to choose a directly executed pre-consumption boundary.

No extra input is posted, no direct callback is invoked, and no event's type/rawType/coordinates are repaired. The two MouseDown cases are a correction to the expected native control semantics, not permission to accept arbitrary mouse activity. All other click requests retain MouseUp. Observation still fails if the expected actual event never reaches the owned control, even if the worker reports successful posting.
