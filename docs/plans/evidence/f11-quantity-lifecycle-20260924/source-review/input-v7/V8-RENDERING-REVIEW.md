# F11 v8 rendering prerequisite: independent diagnosis

Review by `work_cadence_finish`, 2026-09-24. No product, fixture, controller, worker, frozen selection or native process was changed for this review. The original v6, v7 and v8 failures remain failures. Root owns the next implementation and native decision.

## Findings

1. **The v6 click reached the real product.** In `c6d7f948ce984e02a1fa2c16eaba018d`, event 67 requests the observed gear button at actual 2560x1440; events 68 and 69 record the actual native button result and quantity-menu action. Its missing Root-level event acknowledgement is an observer failure, not evidence that PostMessage failed. V7 correctly moved acknowledgement to the managed play UI entry. I found no event mutation, synthetic callback, early-returning native prefix or focus operation in that source delta.
2. **V7/v8 fail before any input.** Both captures pass the native 1024x768/windowed/preferences/scale assertion and load the actual Italian translation. Both time out at `render/open-gear`, before observed geometry or an input request. V8 is 39/41, U0, with zero posted requests. Root/play counters are event-bearing entries only: `GuiBefore` ignores `Event.current == null`. They do not prove that every possible callback invocation was absent. The independent absence of gear repaint geometry remains meaningful.
3. **V8 proves early window visibility, not visibility at the failing step.** Its exact PID/creation-time/HWND/class/private-thread receipt records hidden 304x201 becoming visible, noniconic 1024x768 after one `ShowWindowAsync(4)`. The receipt finishes at **12:48:48.387801Z**. Harness start is 12:48:59.1669296Z; `render/open-gear` starts **12:49:37.1908165Z** and fails at 12:49:45.1991585Z. `native-input.py` does not call `window_state` again until an input request exists. There was none. Thus the capture does not establish the window's visibility/size at the failed render boundary, about 49 seconds later. This is an observation gap, not proof that Unity hid it again.
4. **There is a credible presentation-mode difference, but no proven engine cause.** Both runs initialize Unity 2022.3.35f1, D3D11 and the same GPU. V6's zero-size native preference defaults cause `PrefsData.Apply` to call `SetNativeResolutionRaw`, whose installed implementation chooses the largest advertised resolution and passes `!BorderlessFullscreen`. No `-popupwindow` is present. V7's explicit 1024x768/False preferences avoid this path. V6 emits D3D refresh/vsync fallback notices absent in V7/v8. Neither run records `Screen.fullScreenMode` or the actual swap-chain type, so do not assert that V6 used exclusive fullscreen or that a particular DXGI status caused V8.
5. **There is no evidence justifying a different input route.** Native Update and the bounded wall-clock steps continue. `runInBackground` is already enabled; it is not proof of rendering. The V8 private-desktop receipt records Default throughout, no switch, controller exit 0, joined cleanup and zero owned processes afterward. A rendering prerequisite failure is not a quantity-feature regression.

## Recommended smallest discriminating run

Keep the current product and host, the native 1024x768/windowed preferences, existing hidden launch/private desktop, one conditional no-activate show, actual play-UI observer, all input/state oracles and the existing bounded timeout. Add **only `-force-d3d11-bitblt-model`** to this controller's producer arguments. Do not change graphics API, UI scale, resolution or fullscreen preferences simultaneously.

Add passive bounded window-state observations to the existing worker while it is waiting for requests: retain the exact bound HWND/PID/creation-time/private-thread checks, record state changes plus a sample at `render/open-gear` and at terminal/timeout, and keep checking the input desktop. This supplies evidence at the relevant boundary without another show operation or an input substitute. Use the existing events stream or a small explicit diagnostic marker; no new general monitoring framework is needed. No host rebuild is necessary for this one discriminator.

Unity documents the flag as selecting the older D3D11 BitBlt presentation model. Its documentation says D3D11 normally uses the flip model, while exclusive fullscreen falls back to BitBlt. This makes the flag an evidence-based hypothesis with fewer changed variables than recreating V6 fullscreen. It does **not** promise rendering on an inactive desktop. [Unity player arguments](https://docs.unity3d.com/2022.3/Documentation/Manual/PlayerCommandLineArguments.html), [Unity D3D11 presentation setting](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/PlayerSettings-useFlipModelSwapchain.html).

Accept rendering only from native managed play-UI event/repaint observations and actual gear geometry. Then retain the existing request → owned receipt → native event → real control → real physical result chain. A successful producer may proceed through its existing tests; a failure is retained without another fullscreen or focus attempt. If it fails with a late visible/noniconic window, the evidence narrows the issue to rendering/callback delivery beyond simple hidden-window state. If the window became hidden, that new evidence must be evaluated separately; this proposal does not repeatedly show it.

This is a rendering-environment test, not a product change. It keeps the constrained translated 1024x768 render acceptance and avoids a global display-mode transition. Record the exact new command line and actual Screen/Prefs assertion already provided by the host. Optional display configuration observations must be read-only; no display setters belong in this test.

## Borderless alternative, if later needed

Do not rerun V6 by omitting width/height preferences: the native game selects its largest advertised resolution and uses a boolean fullscreen API, which does not establish safe borderless behavior. `-popupwindow` also has distinct game semantics: native `ResolutionUtility.BorderlessFullscreen` recognizes it and forces its resolution calls to `fullScreen=false`.

Unity documents `-window-mode borderless` and `FullScreenMode.FullScreenWindow` separately. A later explicitly reviewed borderless diagnostic would need current-display dimensions (not the game's largest-mode heuristic), explicit nonexclusive mode from startup, actual `Screen.fullScreenMode` and window observations, and read-only before/during/after display-configuration equality. It must retain the inactive desktop and forbid focus/activation, desktop switching, physical input and global display setters. Do not claim that the V6 capture proves these conditions. [Unity borderless mode](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/FullScreenMode.FullScreenWindow.html).

A native-resolution-only render would not by itself fulfill the current 1024x768 screenshot oracle. Any later viewport adaptation must explicitly preserve the contract's real translated constrained-layout coverage, not silently waive it. The smaller windowed presentation test above avoids that additional issue.
