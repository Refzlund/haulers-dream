Implement the **saved explicit order and its job lifecycle** next. It is a useful bounded implementation task that can proceed before the unfinished shared capacity allocator. Do not expose a destination command backed by vanilla HaulToCell while waiting for that allocator: that would contradict the requested exact point/shelf, total quantity and custody behavior. This recommendation retains the entire existing acceptance plan; neither F12 nor F13 is implemented or completed by this investigation.

These are existing building blocks with outstanding integration work, not a working reservation or custody service.

## Slice A: persisted intent, actual job links and cancellation

The authoring unit should be small: a concrete order record plus one owner/helper, two integrations in existing component/job-def/save code, and narrow lifecycle hooks. Keep actual physical operations out of this first slice until their admission/custody dependencies exist. No menu should offer a job that cannot yet carry out its contract.

1. Add `ExplicitHaulOrder.cs` with an IExposable order record. Its immutable intent is per-pawn monotonic order ID, actor reference/ID, original map reference/ID, original source reference plus retained original Thing ID, requested total, destination kind, exact point or concrete shelf reference/ID, and shelf placement identity at confirmation. The original source ID remains historical even if its full stack later becomes carried or is absorbed. Never replace it by a search for matching defs. Store delivered total, phase/reason, current trip generation/count/source/cell, actual owned cargo slices, and current Job loadID separately. Empty cargo is a valid initial value; do not fabricate a custody receipt to fill it.

2. Extend the existing pawn component with a deep-scribed order list and next per-pawn ID. Supply a compact `ExplicitHaulOrders` owner for creation, binding, current-driver lookup, terminal transitions and post-load reconciliation. Allocate IDs only in the synced commit, not UI rendering/targeting, and use no random Guid for persistent order identity. Retain terminal cancellation long enough that stale job callbacks cannot restart it. A total of 100 remains 100 when trips carry 35, 35 and 30; job.count is a trip limit, never the requested total. New pickup may not consume units already represented by unresolved owned cargo.

3. Link the native job by its scribed `Job.loadID`, with the component's independent order ID as authority. Maintain an exact transient current Job/driver reference check while running. After load, search only that pawn's actual current/queued jobs for the recorded dedicated definition/loadID and validated trip targets; zero or multiple matches pause with a reason. Do not recreate a missing queued job automatically, and do not retain only a pooled Job reference. Native Job.Clone copies loadID, so duplicates must be rejected as ambiguous. A narrowly scoped Job.source reference to a deep-scribed ILoadReferenceable order is an alternative, but it adds a cross-reference contract; the existing loadID bridge is sufficient for this slice and avoids new global Job serialization patches.

4. The dedicated `JobDriver_ExplicitHaul.IsSameJobAs` must distinguish order IDs. Native JobIsSameAs consults that override but its default comparison ignores count. Two new requests for 7 and 9 at the same source/destination are distinct orders; the same existing order can be recognized after a fresh driver is created. Driver state is not authority: native StartJob calls MakeDriver on every resumed start. Speculative/queued TryMakePreToilReservations calls validate identity without acquiring cargo/destination allocations; actual admission requires `pawn.CurJob == job` and the current driver instance. The eventual JobDef disables opportunistic prefix/suffix and duplicate-source collection, while deliberately supporting suspension.

5. Integrate queue removal before native QueuedJob.Cleanup clears/returns its Job to the pool. Capture the exact order/link before the native body; cancel only a verified explicit order. **Do not equate all cleanup calls with cancellation:** native CaptureAndClearJobQueue first copies wrappers containing the same Job objects, then invokes cleanup with canReturnToPool=false. Add a narrow capture/restore context so this remains detached/suspended intent, not cancelled intent. canReturnToPool alone is not a general cancellation reason. RestoreCapturedJobs can also discard later jobs directly to the pool after a failed restoration; cover that bounded path or leave the affected links paused after exact reconciliation. Dequeue/Extract normally promote or transfer a job and must not cancel it.

6. Handle active suspension and cancellation separately. Native SuspendCurrentJob enqueues the same Job before CleanupCurrentJob; native cleanup invokes driver Cleanup before its eventual carry-drop and Job return. A driver finish action cannot by itself observe the later drop/merge. Capture the order and actual cargo before cleanup, then reconcile the complete cleanup boundary before changing its custody state. Before pickup, terminal cleanup cancels/retires the pending order. With owned cargo, cancellation releases future claims and transfers the actual remainder to explicit recovery; it does not credit delivery. Do not add a tick loop that silently restarts blocked or cancelled orders.

7. **Resolve normal-save stripping in the same slice.** `Patch_ScribeSaver_InitSaving.StripSet` is currently copied from HdJobDefSets.CustomDriverJobDefs and removes matching queued jobs whenever cleanupOnSave is enabled. Simply adding the new driver to that set would erase requested queued/suspended persistence. Keep the explicit driver recognized by the existing cargo/softlock safety groups where appropriate, but give pre-save stripping a separate semantic set that excludes this persisted-order job. Preserve current cleanup of existing transient HD jobs; do not globally disable the setting or interrupt current jobs during serialization. Reconcile after cross-references/job loading finishes, not during LoadingVars and not by mutating claims midway through saving.

Concrete next authoring assignment: implement the order record/component owner, exact native job-link/dedup behavior, narrowly scoped queue/capture lifecycle and save-strip distinction together. Add only the dedicated definition/driver surface needed by those boundaries. Keep physical toils and command publication disconnected until Slice B is implemented. Review this source change against native lifecycle behavior below; do not replace it with another plan-only approval chain.

## Slice B: a controlled trip using shared physical admission

This is the next required implementation after Slice A, not an optional extension. It depends on actual resource allocation (the storage-capacity plan), a bare-cell observation adapter, and observed hand-cargo transfers. It need not wait for unrelated bill/refuel/menu work.

Use one selected-source hand-carry trip at a time. Before pickup, validate remaining intent, actual source/owner, actor/map, selected destination, and live carry capacity. Reserve only the bounded trip amount and allocate physical destination resources in the same shared admission owner used by other HD/native incoming cargo. Do not implement a parallel per-explicit-order def ledger, and do not use FreeUnitsFor(int.MaxValue/unknown) as proof of room. Allocation identity remains runtime-derived and must be reacquired after load; persisted intent and custody are different from a saved hard cell reservation.

For a shelf, observe the canonical linked group for shared accounting but restrict the permitted resource set to cells whose concrete parent is the selected shelf. Another cell on that shelf is valid; a linked sibling or a new shelf at the same coordinates is not. Retain expected position/map identity and pause on moving, despawning or minifying until an explicit valid resumption decision. Preserve fixed/effective filters, directional stack compatibility, provider and HD-denial predicates. A point in existing storage keeps its actual filters but can use only that exact cell. A bare point needs an explicit physical-cell observation path, sharing the existing slot/top-up records and guards without pretending that a null SlotGroup is supported.

Adopt a **no-steal** explicit-source reservation policy initially. Native ReservationManager.Reserve can interrupt other current/queued jobs when job.playerForced is true. A final narrow explicit-job reservation boundary must suppress that forced takeover while preserving ordinary reservations and reporting blocked state; passing ignoreOtherReservations=false alone does not suppress native forced fallback. Do not temporarily flip another live job's flags. If the shared allocator later supports an accounted handoff, make it an explicit separate transaction rather than inheriting forced behavior accidentally.

Pickup records the actual SplitOff/hand owner and quantity. Place via the count-limited `Pawn_CarryTracker.TryDropCarriedThing(cell, count, ThingPlaceMode.Direct, ..., placedAction)` in a controlled toil; retain native notifications and revalidate the exact cell/allocation first. Native placement may transfer 3 of 7 into a 72/75 stack and return false with 4 still held. Credit only verified callback receivers/count deltas at the selected destination, release exactly those accepted claims once, and retain the 4 as owned cargo. Never credit a whole trip from the boolean, and never send the remainder to another shelf. An exception after a partial callback retains that actual progress and the primary failure.

Observe the actual cleanup drop/split/merge boundary before claiming interruption/resume. The pure CargoPhysicalSession receipt types can support this accounting, but currently have no production capture or persistence adapter. Add the narrow adapter around the explicit carry operations and relevant native cleanup, with unsupported/unobserved mutation causing a paused recovery reason. Do not serialize session-local Guid handles as durable saved custody. On reload, rebind only actual recorded Thing/owner identities and validated quantities; uncertainty pauses rather than claiming any same-def stock. Retain all existing cargo-loss, death/despawn/map-exit and cancellation requirements.

Within the same order, continue with bounded subsequent trips until the unchanged total is delivered or a reasoned block occurs. Source growth does not enlarge the total; exhausted/replaced source preserves partial progress. Full or invalid destination does not trigger a tight retry loop. Manual resume must revalidate the same intent and remaining custody. This supports repeated trips without silently substituting a different source or destination.
