## Challenged boundaries

1. **Cancellation scope and reservation ownership.** Native Reserve installs the forcing reservation before traversing a copied reservation list and cancelling displaced jobs (`ReservationManager.cs.txt:300`). The wrapper can therefore release one validated old row without invalidating that native enumeration. It requires the same actual manager/map, spawned Item source, default layer, forced job, primary target, supported exact driver identity, and an actual new exclusive reservation. Bulk jobs additionally require the original positive slot-zero source. Old jobs must be the exact current/queued bulk job with aligned pickup lists and no unexpected A queue. Unsupported drivers, foreign/non-hauling jobs, building interaction reservations, ambiguous layers/duplicate old rows and direct cancellations retain the original native call with all arguments. This does not suppress InterruptForced globally.

2. **Failed-reservation and query purity.** The success postfix checks both `__result` and actual ownership; the wrapper occurs only in the native success branch. CanReserve/menu probes do not cross this mutation seam. A native failed Reserve has no retirement path. This is a reservation-level guarantee: a multi-reservation job could later fail another admission requirement after a successful source reservation, as native cancellation already could. The fixture must not mislabel later job failure as a false Reserve result. Driver admission checks CanReserve before reserving incidental extras; only the original anchor retains force permission.

3. **Current, future and queued work.** Retirement replaces every matching pickup with Invalid/zero and never removes list entries. Matching obsolete A/B/C references are cleared, so scalar readers cannot retain a false claim. The original cursor, job ID, queue wrapper/order, future slots, `loadedAnything`, cargo manifest, tags and keep values are unchanged. Current walk/pause recovery stops the path and advances exactly once at its own safe pre-tick. Native DriverTick rechecks a changed toil after each pre-tick action (`Verse.AI.JobDriver.cs.txt:388`), so it returns instead of continuing against the old toil. If a delay expires first, the existing take guard sees Invalid/zero and performs the same single skip. No other pawn's next reservation is run inside Reserve.

4. **Held cargo and same-tick claims.** The retirement path preserves destination rows and invalidates only route/plan memos plus storage evidence generation. `StorageCommitments.UnitsMoving` keys its memo on that generation. `StorageEvidence.AddPlannedPickups` skips Invalid targets, while `AddPocketedSurplus` still includes actually held tagged surplus after keep subtraction. This avoids the zero-count/full-stack fallback and retains carried cargo protection. No whole-ledger clear, def-wide claim drop, inventory transfer or tag mutation is introduced. Existing destination-capacity interruption remains a separate rule and needs its own focused native control.

5. **Save and toil stability.** The change adds no saved field or process-local retirement registry. Native Job serializes the queues and scalar targets/counts; existing driver serialization retains `loadIndex`, `loadedAnything` and nearby cargo. The yield count/order is unchanged: attaching pre-tick actions to existing walk/pause toils does not shift `curToilIndex`. A fully retired aligned plan is admitted without promoting another slot to primary authority and reaches its ordinary finish path. Identified queued nearby orders remain covered by the existing save exemption, whose predicate does not depend on targetA validity. Actual invalid-target serialization, native path restoration and restarted physical delivery still require the planned producer/restart evidence.

6. **Binding and determinism.** The transpiler checks the instance nine-argument signature and all three cancellation call sites before returning rewritten code; the added receiver/context arguments preserve the original receiver and four call arguments, with layer at argument 6. Incoming labels move to the first inserted load; unsupported exception-block shape leaves the original method and disables the success postfix. This source reasoning does not replace checking the actual patched IL. The postfix sorts a copied pawn list by thing ID and preserves queue order, consumes no RNG, and runs on native reservation mutation. It is not evidence of an actual Multiplayer session.

## Concrete acceptance-design correction

The original `../native-fixture-design.md` step 4 proposed obtaining an **unreserved** queued nearby plan through `NearbyHaulCommand.IssueSynced(..., queue:true)`. That path calls native TryTakeOrderedJob, whose queue branch calls `job.TryMakePreToilReservations` before `EnqueueLast` (`Pawn_JobTracker.cs.txt:941–946`). The current nearby reservation prefix only rejects invalid permissions; it does not defer valid reservations. Therefore this cannot supply the required unreserved slot-zero witness.

Keep the real command-created **reserved queued** case. Test the separate success-postfix/soft-queue behavior through an explicitly justified native JobQueue input or a demonstrated real lifecycle producer that leaves the queue unreserved, using an actual built plan and never fabricating the expected retired output. Require a measured absence of native reservation before handoff. I sent this finding to the author; it is a fixture design issue, not a reason to remove the useful postfix or broaden product scope.

The remaining native contract is the existing bounded one: old-behavior reproduction; current/future/reserved and genuinely unreserved queue handoff; failed Reserve/query purity; incidental-extra control; original native cancellation; held surplus and constrained storage; actual save/restart; and physical completion/conservation with retained queue intent. F38 remains open until that evidence passes independent review.
