## Implemented behavior

`JobDriver_UnloadTransporterInBulk` owns its current trip, rather than delegating a storage job and assuming it succeeded. The actual no-merge pulled Thing references and remaining quantities, hands reference, pending pull mode, pull counter and physical pulled/delivered totals are scribed. It enters through live admission; each physical pull rechecks flag, feature, actor, cargo owner/count, draft, forbidden policy and current load custody after the visual delay. Passengers never enter selection. Multiple haulers can share the hold because each transfer operates against its current actual owner/count.

The driver searches for accepted storage before pulling and again before delivery. Automatic admission refuses a hold with no eligible supported storage destination, preventing repeated zero-progress dispatches. The shared pull helper lazily probes only a selected candidate's storage availability, including the actual CE hands fallback; candidates with no destination are removed from that finite selection. Scanner/menu storage probes use `needAccurateResult:false` and consume no Rand. An actual in-tick delivery plans afresh using the normal storage search.

Delivery uses native walking/container transfer, or the native **direct** cell placement API. It deliberately does not use `PlaceHauledThingInCell`'s general storage fallback: the installed native source can drop aside or destroy the carried stack if it cannot place it. At a cell, the actual placement callback must report accepted units at the selected cell; at a container, native transfer must reduce the actual hands stack and increase the actual destination count. Positive delivery credit is bounded by both facts. A full/withdrawn/refusing destination, no physical progress, missing ownership or a new keep rule ends the operation. It never treats a queued job, disappeared Thing, destruction, or dropped-aside stack as successful storage.

Automatic work ends after one complete trip. A player-forced order returns to the same hold only when every pulled unit from the prior trip has been stored, its cargo list is drained, current admission still succeeds, and the queue is empty. Each pull loop is bounded; each delivery loop must physically store positive units. Drafting or feature disable ends the operation. A new explicit command interrupts it normally, and queued work prevents another trip. Turning a standing unload flag off or losing load custody prevents any further pull; already-owned cargo may complete its storage leg. Ending an order never grants a new intake authority or recreates the priority order. An enabled standing flag can still provide later ordinary automatic work, as intended by the separate toggle.

`BulkUnloadRecovery` appends ordinary recovery behind existing work on **every** ending. It tags only recorded cargo still in the pawn's inventory; ordinary surplus/keep rules remain authoritative. Hands recovery requires the saved actual Thing and sufficient recorded owned quantity. It never adopts arbitrary replacement hands. The helper does not call `PawnUnloadChecker.CheckIfShouldUnload`: that helper can insert SelfPickup at the front of a queue, even with its behind-work flag. Instead it appends just the normal inventory recovery (or ordinary away-map pack-animal recovery). Drafted inventory remains tagged for the normal later recovery opportunity. No reachable destination can mean cargo stays held; that does not earn a successor or become a success claim.

The carrier driver now records visit cargo, hands Thing/count and pending pull mode with append-only labels, retains `hdUcibPullLoops`, and uses the same all-ending recovery. A pre-feature save may reconstruct a lost hands reference only when its existing scratch target is demonstrably the actual carried Thing; it does not infer ownership of unrelated hands. This fixes new saves made after either hands or inventory pulls. Historical saves that never serialized a split stack's identity cannot reconstruct missing provenance by assertion; the normal existing tag/recovery paths remain the fallback.

Prioritized transporter loading now records actual positive deposits (`hdLtibDeliveredUnits`). After a successful visit it releases old ledger claims and retags survivors **before** replanning the same current group. A successor is merely queued and obtains its own claims only at actual start. It needs real deposits, an undrafted live pawn, a valid enabled target and an empty queue. No reachable new plan ends the priority operation; it cannot hop around a still-incomplete selected manifest. Cross-target ContinuousLoad remains a separate opt-in and requires selected-target completion, an undrafted pawn and no queued work. This changes the old drafted-chain promise: UI/translations must describe the final rule rather than retaining that claim. The first existing drafted loading visit remains supported; a new continuation does not run while drafted.

## Ownership and lifecycle corrections

The installed `CompTransporter.TryRemoveLord(Map)` is not teardown: it can return without removing a lord, and successful removal leaves the group/manifest unchanged. The session-ending patch now runs at actual `CleanUpLoadingVars(Map)`, capturing the old group before native cleanup. `ConflictActive` treats an existing manifest as authoritative even without recorded session history, short-circuiting that common case before scanning pawn queues. This is deliberately conservative for old saves: fulfil or explicitly cancel a pending/stale manifest before unloading. Missing history never grants permission to take cargo ahead of its first courier. No fabricated “old load accepted” event is written. Current lord/courier/queued-loader custody still blocks after the manifest drains.

Scanner cost: feature/flag/empty-cargo and actor checks occur before the live custody scan. Unflagged, unsupported, empty or actor-ineligible pairs never scan pawn queues. Open manifests also avoid that scan. Eligible flagged holds with drained manifests must still inspect current jobs/queues; there is no cached permission at the physical transfer boundary. This is a deliberate correctness choice; large numbers of simultaneously flagged holds remain a native performance observation, not an unmeasured performance claim.
