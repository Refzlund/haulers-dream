## Required corrections found in actual proposal source

1. **Conflict polling never starts at normal positive game ticks.** Driver lines331/338 initialize lastConflictScanTick to int.MinValue, then compare `ticks - lastConflictScanTick < 60` without a sentinel exception. In unchecked C#, tick2 produces -2147483646, so the method returns before setting the timestamp or inspecting conflicts. Fix the first-call test explicitly. More importantly, use a cheap current ownership/session check at every transfer; a60-tick diagnostic scan must not authorize cargo removal after a synchronous load takeover.
2. **Stale jobs bypass admission.** Driver entry only checks target existence plus that broken conflict check. It never rechecks feature, flag, VF exclusion, actor inventory/component/empty hands/permission, or automatic forbid policy after its visual wait. WorkGiver.JobOnThing constructs a job without consulting HasJobOnThing. Centralize a side-effect-free admission answer for menus/scanner/job start and revalidate the relevant live facts at transfer. Synced SetBulkUnloadAll currently writes only an integer flag; validate the actual target and load ownership when the command is applied, not only when the gizmo was drawn. Turning off must remain possible without satisfying turn-on admission.
3. **Feature-off can still block loading.** The gizmo postfix correctly disappears at runtime disable, but UnloadFlagActive and the two TransportLoad guards ignore enableBulkUnloadTransporters. A retained flag on an idle loaded hold therefore still blocks HD loading while vanilla's load gizmo is enabled. Define inactive flags when disabled, or clear through a deterministic state transition, and invalidate same-tick load/menu probes. Also remove patch-time Prepare suppression for the new gizmo: starting disabled and enabling later must work without a settings-save patch cycle.
4. **Group and in-flight exclusion are incomplete.** The new load gates inspect only adapter.Primary, although an adapter can deposit into other members. Inspect the relevant whole group/actual destination and protect an already-running loader's deposit. ConflictActive returns false immediately when the manifest is empty, before checking a remaining lord/courier; do not infer that outstanding in-flight custody is harmless solely from an empty manifest. Prove release using actual load completion/cancellation and live custody. Fresh pure-cargo acceptance, top-up, rejected acceptance, cancel, launch/return and native item-drain transitions need distinct checks.
5. **Drafted order promise is not implemented.** The menu advertises Drafted=true, but driver line294 delegates backpack delivery to PawnUnloadChecker, whose current unconditional drafted guard correctly refuses it. A drafted ordered visit can therefore queue another visit without the promised backpack storage trip. Keep the global draft guard. Smallest supported scope is an explicit undrafted-only transporter unload command with a clear disabled reason, including recheck if drafted mid-operation. If drafted transport unloading is intentionally required, it needs its own bounded cargo delivery authority and native proof; do not reuse F07 nearby-order authority on an unrelated job.
6. **Save/interruption and delivery completion need real ownership checks.** `unitsMoved` and `handTail` are unscribed. After reload between transfer and finalize, no code actually reconstructs handTail despite the comment, and unitsMoved0 suppresses the intended successor. Finalize is a toil, not an all-ending cleanup hook, so interruption/conflict bypasses it. Track/rederive actual carried cargo, recover it behind replacement player work, and never restart a cancelled priority operation. A queued storage job is not proof of delivered cargo: destination rejection/full storage must stop follow-up pulling without loss, duplication or a walk loop.
7. **Eligibility, UI and descriptions drift.** Automatic admission has a master check and HaulOrderGate but omits the usual automatic actor eligibility; preserve allowMechanoids/native robot roles/directed-activity behavior rather than letting the new work giver bypass it. Gizmo code disables only the first emitted load command when its own toggle was inserted, and comments still say single visit/player-only/all-forbidden-clears while actual behavior differs. A hold with only forbidden goods must remain available for an explicit override or manual toggle-off; do not silently erase intent based on one pawn's restrictions. Exact corpse/CE/driver behavior, UI wording and translated placeholders must agree.

The current five MayOffer tests exercise only a three-boolean expression. They do not verify these lifecycle, custody, queue, setting or save boundaries.

## Recommended consistent order semantics

Use the selected operation as the unit in both directions: **prioritize loading this group until its currently committed manifest is fulfilled; prioritize unloading this flagged hold until its eligible cargo is delivered.** Automatic work remains one native visit followed by normal scheduling. The existing opt-in ContinuousLoad remains the separate choice to proceed to other targets after the selected target completes.

For loading, replan the same target only after real successful deposits, release/settle the old claims before planning, and claim the next visit only when that job starts. For unloading, deliver the current pulled cargo first and revalidate the same hold before the next visit. No progress, no reachable/accepted destination, cancellation, drafted state, removed flag, feature disable, departure or load takeover ends continuation. New player orders retain priority; continuation must not clear, displace or indefinitely starve explicit queued work. A failed/interrupted visit never earns a successor. This resolves the author's consistency request without collapsing a deliberate multi-trip order into a single visit or silently enabling cross-target loading.
