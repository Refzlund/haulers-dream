## Source-proven bypass

SRH's `StoreUtility_Patch.Before_TryFindBestBetterStoreCellForWorker` asks the actual storage settings' controller before the native per-group search. Its `WorkGiver_CookFillHopper` prefix similarly rejects a paused hopper before creating a job. Its `NoStorageBlockersIn` postfix applies only inside the native merge-work-giver scope. Ordinary `IsGoodStoreCell` calls deliberately remain usable by deliveries already in progress.

HD's `HaulToStack` postfix runs **after** the native storage search and searches other equal-priority groups for a partial stack. The released v1.24.0 and pre-F20 source check ordinary `IsGoodStoreCell`, not the SRH group gate. Thus the native search can reject a paused hopper shelf and choose an empty equal-priority store, after which HD reroutes back into that shelf's partial stack. `EnRoutePickup.FindMidwayStoreCell` and `StorageRouting.FindBeforeCarryStoreCell` independently scan groups and have the same new-destination bypass. This is a concrete code defect even though its contribution to every logged trip requires actual runtime evidence.

The new optional `StorageRefillHysteresisCompat` resolves the provider's exact public `GetHysteresis(StorageSettings)` and `AllowsRefill()` methods. All three new-destination searches use that answer. No SRH type enters a product signature, and no new assembly dependency is added. Missing/inactive SRH leaves existing behavior unchanged. An active provider whose API cannot bind emits one warning and disables only these HD shortcuts, preserving the native storage search instead of guessing at thresholds.

Stack refinement checks SRH once on the first relevant partial in a group, after existing radius/room/budget filters. It does not measure distant irrelevant groups. A cached positive cell rechecks SRH; cached negative results are not reused while SRH is present, because the provider's manual toggle can reopen a destination inside the same paused tick. The provider controls its own usage cache and latch; HD does not cache that answer or retain a storage owner. Same-tick open→paused→open at intermediate fullness therefore needs an actual regression observation.

## Threshold semantics that acceptance must preserve

SRH sums each storable stack's `stackCount / def.stackLimit` and divides by the owner's total supported stack slots. A linked group uses all its members through the group's actual shared `StorageSettings`. For a three-slot shelf with ordinary corn stack limit 75, 150 corn is 2/3 full; it is not 150% and not one full stack. Mixed definitions use their own native stack limits.

`AllowsRefill()` opens below the lower threshold, closes at/above the upper threshold, and preserves the previous/manual latch between them. Disabled SRH permits refilling. Usage is sampled through the provider's own configurable cache (default 100 game ticks). The author explicitly allows deliveries already underway to finish and permits overshoot. Consequently 95% is **not** a hard incoming-item cap; adding such a cap or aborting an assigned haul would contradict this provider. Native tests must wait past the actual sampling interval after changing stock rather than overwrite its private cache.

The older ledger connects this report to storage-overhaul work and PR252's unresolved foreign count-clamp limitation. No retained evidence proves that this exact SRH gate was previously repaired and then regressed. Classify as an unresolved compatibility gap with related storage history, not a proven recurring post-fix SRH failure. F16 and unrelated overdelivery reports remain separate.
