# F38 initial reservation diagnosis

24 September 2026. Root source investigation during the F41 native producer. No implementation or runtime acceptance yet.

Frozen source GH266 reports that ordering a second pawn to haul any item reserved by the first nearby sweep cancels the first pawn's whole job. It requests multiple pawns working in the same area. The reported version is 1.24.0.0, game1.6.4871 rev591. Use the retained body in scoped-feedback-register.json; no additional collection is needed.

`JobDriver_BulkHaul.TryMakePreToilReservations` reserves the first pickup and then ReserveAsManyAsPossible over the whole queue. Its later per-stack invalidity and path-failure handling deliberately skips one step rather than cancelling the sweep. That later logic cannot handle forced reservation takeover: actual installed `ReservationManager.Reserve` adds the new forced claimant then directly invokes `EndCurrentOrQueuedJob(oldReservation.Job, InterruptForced)` for the displaced target. This ends the whole sweep before its next per-stack validity check.

The installed native source is retained at `f41-unfinished-implementation-20260924/native-fixture/ReservationManager.cs.txt` (source lines327–339). This is a source-supported mechanism, not yet a paired native reproduction of GH266. The existing driver comment references earlier issue160's pathing fix; pathing and forced reservation displacement are different cancellation boundaries. F07 queue authority fixes do not by themselves change this native displacement.

Simply removing reservations for future pickups is not a complete decision: RouteSelection also treats other jobs' target queues as claims, storage commitments price planned cargo, and another forced order can still take the actively reserved pickup. A scoped handoff must preserve the first job's valid remaining pickups, already held cargo and queued player intent, while giving the explicitly requested target to the new pawn. It must release only that target's old reservation and avoid changing unrelated native/foreign jobs. Current, future and queued sweep targets need separate consideration; no generic suppression of InterruptForced is acceptable.

Candidate acceptance must show the second pawn receives its requested target while the first completes other productive work, with cargo conserved, queued replacement work retained and normal non-hauling cancellation unchanged. Add only relevant save/Multiplayer/shared-claim checks for the chosen implementation. F38 remains open.
