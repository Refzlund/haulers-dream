## Why the optional checks are feature-specific

Current `InventoryDropCommand.cs` resolves exact pawn/map/Thing ID/opening count, calls the native count-taking TryDrop and then explicitly settles caches and Keep/tag state. `Dialog_DropInventoryAmount.cs` additionally captures source and owner references and gates one submission. `Patch_InventoryDropAmount.cs` intercepts the native/CE local row callbacks before their original synchronized/Sidearms callbacks; the CE menu captures original pawn, owner, count and map. These are changed behavior, so targeted provider checks belong to F11 even though the reporter did not name those mods. Broad provider certification and final assembled-PR testing remain separate.

Actual installed provider hashes still match the original reviewed APIs: CE `3102BC2276C583E51FE85AE340E5B986F80452171DB63EA72D04F7651B96AFE3` and Simple Sidearms selected v1.6 `703FDA907021F9D76CF6DF6941E73B519A7D0A28B022D67ACAFAED44A40A1F40`. This audit freshly decompiled the three retained native source files here. CE CompInventory.UpdateInventory recomputes weight/bulk, weapon lists and ammo references; CanFit reads those cached values. It can also set a matching existing HoldRecord.pickedUp=true. Measure actual hold counts/intent and this marker rather than assuming a refresh is entirely side-effect free. A normal previously picked-up retained item is the primary control; do not call a fabricated inconsistent hold record a reported bug.

Requiring all matching preferences to remain after intentional final departure would be the wrong oracle.
