## Observed native path

The exact installed native Assembly-CSharp5CF1B5BE399D5B1C9C56CA72C9D35B4ECF307FEACF5859D04AC5A1AA5926356A was decompiled into `%TEMP%/haulersdream-partial-drop-design-20260908`. InterfaceDrop orders removal jobs for worn/equipped gear, but inventory uses the whole-stack ThingOwner.TryDrop overload. It refuses destroyOnDrop items. No native inventory quantity picker is present on this path.

The native count-taking TryDrop overload already supports splitting a partial amount, placing it near the actor and reabsorbing the remainder when placement fails. Unlike a whole removal, a successful partial split does not call the owner's NotifyRemoved. A false placement return can still represent partial placement; success/count reporting therefore needs actual before/after evidence. The dropped result may be an existing destination stack. Do not manually remove the retained source or report the resulting target's total count as the quantity dropped.

HD's existing Gear-tab chip controls a per-def retained amount. It is not a drop command. InventoryDrop.TryDropPreferHome serves automatic unloading and has different placement intent; a player dropping from inventory should retain the native near-actor semantics. Existing kept counts are preferences and should not be silently rewritten by a partial drop. Only a fully departed tracked reference should be deregistered; retain the source's cargo tag when it remains held. The present CE compatibility comment assumes owner notifications maintain its cache; the partial native path lacks a removal notification, so actual CE hooks must be inspected and the resulting weight/bulk cache verified rather than relying on that comment.

## Required behavior

- Provide a discoverable quantity selection for a stack in a pawn's inventory, with an exact number field, a bounded slider and explicit confirm/cancel. Closing, Escape or cancelling must not drop anything. Non-stackable items keep their existing native behavior.
- Preserve the native equipment/apparel, quest-lodger, locked gear and bandwidth decisions. Do not add a blanket colonist-only restriction to an inventory control that native RimWorld permits for other controllable pawns.
- Bind the pending action to the actual pawn, inventory owner and Thing identity. Recheck controllability, map/spawned state, ownership, destroyOnDrop and available count when executing. A stale selection must never act on another pawn/stack or over-request the owner. Choose and document an explicit changed-count policy during focused design review.
- Submit the mutation exactly once through the existing optional Multiplayer integration. UI/dialog creation must stay local; no dialog inside synchronized replay, no per-frame world writes or hard runtime MP dependency. Inspect MP's actual native Gear-tab hook before choosing the interception point; an InterfaceDrop prefix may otherwise run at the wrong synchronization boundary.
- Use native quantity placement and preserve physical conservation, remainder custody and subsequent unload/keep behavior. Keep intended placement distinct from automatic storage selection. Refresh any supported compatibility state whose actual hooks are bypassed by partial splitting.
- Translate new strings in every supported language and render-check the dialog, including long translations and UI scaling. Do not squeeze a new overlapping button into the existing Gear-tab keep/mass/drop area.
