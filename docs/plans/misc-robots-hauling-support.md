## Exact robot identity, custody and work routes

The base 1.6 `Defs/ThingDefs/AIRobot_Races.xml:4-49` declares Base_X2_AIRobot directly, with thingClass AIRobot.X2_AIRobot, category Pawn, and a comps node containing CompAttachBase. Native RaceProperties.IsMechanoid compares flesh type, whereas Humanlike compares intelligence: these are mechanoid, nonhumanlike pawns, not animals that need allowAnimals.

The actual class extends Pawn. Its creator `X2_Building_AIRobotCreator.CreateRobot(string, IntVec3, Map, Faction)` calls PawnGenerator, supplies custom workSettings, creates an inventory tracker if absent, and ensures equipment/apparel/royalty before spawning. `X2_AIRobot.SpawnSetup` schedules its additional setup, including skills, story, relations and an all-work timetable. The old source comment about inability to draft is historical commentary, not decisive current behavior; the active XML think tree includes queued jobs followed by JobGiver_Orders. Observe actual drafter state in the host rather than manufacturing one or assuming that comment still describes native 1.6.

`robot-work-type-census.json` extracts every one of the 35 concrete R++ definitions. ## Confirmed gaps and competing explanations

**A. Missing component is a source-confirmed intake and recovery gate.** HD `Patches/HaulersDream_Pawns.xml:8` matches only thingClass equal to Pawn. Its SHA is **919A4E3883CC409F5AFAB131BF86184206B3538EAF82D8BE5B8E90B6867F9286**. No runtime HD component-injection fallback was found. Both BulkHaul.HasPotentialBulkWork (around 580) and BuildBulkJob (around 709) require CompHauledToInventory and an inventory. PawnUnloadChecker.CheckIfShouldUnload exits at its first component check (line 31). The selection gizmo postfix also requires that component. Giving a robot an inventory does not satisfy these gates.

This is corroborated by the actual R++ `RPP_PickUpAndHaul_Patch.xml`: when PUAH is present it expressly attaches PUAH's different tracking component to Base_X2_AIRobot. That patch does not supply HD's component. The clean source combination therefore leaves the robots without HD tracking. Other unknown user mods could add it, so inspect final resolved definitions and live AllComps rather than treating this static prediction as an executed-save fact.

**B. Nearby-haul has a second, independent menu veto.** HD provider line 21 has MechanoidCanDo false; source SHA **0AC20B4E2D9576A910C65C6318F589D534397A41C9FAD14EF95BD3B601B3B7AC**. Native FloatMenuOptionProvider.SelectedPawnValid rejects a mechanoid under that setting. FloatMenuMakerMap consults context.ValidSelectedPawns before GetOptions; therefore these robots never reach HD's component/item checks. Adding only the component cannot repair the menu.

**C. Biotech is a separate native control boundary.** FloatMenuContext's constructor removes pawns whose CanTakeOrder is false. Native Pawn.CanTakeOrder accepts a colony mech, but IsColonyMech itself requires Biotech active, player faction, appropriate host state and no mental state (`Verse.Pawn.cs:554,794`). With Biotech active, an ordinary player-owned Misc. robot passes this test without an overseer comp. Requiring IsColonyMechPlayerControlled instead would incorrectly demand an overseer and exclude the actual base robot. Without Biotech, ToolUser robots are neither colonists nor colony mechs for this menu test. Both mods advertise base-game operation and do not require Biotech; support must make a deliberate scoped provision for this path, not silently introduce a DLC requirement. No relevant global CanTakeOrder/FloatMenu patch was found in the inspected base DLL class census or R++ shipped patch types.

**D. Defaults do not explain the clean failure.** allowMechanoids, bulkHaul and haulNearbyOption default true; per-pawn autoHaulYields defaults true. allowAnimals defaults false but is irrelevant for these flesh types. Hidden showAutoHaulGizmo does not disable automatic hauling. A user setting can still suppress intake: master off, per-pawn opt-out, bulk off, map policy, allowMechanoids off, directed Lord/duty, or item/storage/capacity constraints. These are live-state alternatives to measure, not facts inferred from the comments. The source IsEligible evaluates WorkCapabilityProbe but Core EligibilityPolicy returns allowMechanoids for mechs regardless of the disabled-work boolean. Do not confuse that broad yield/recovery policy with permission for every specialist to perform general storage hauling.

**E. Construction success is fully compatible with both failures.** SharedInventoryPatches' low-priority batch extends a normal floor-resource HaulToContainer job without an inventory component and only up to hands capacity. More significantly, InventoryConstructDelivery's ResourceDeliverJobFor postfix and TryBuild can make **HaulersDream_OverloadConstructDeliver** without an HD component or YieldRouter eligibility check. The driver reads the robot's actual inventory; RegisterLeftoverForUnload returns when the component is absent (`JobDriver_OverloadConstructDeliver.cs:497-510`). Thus the observed building completion could be actual HD inventory construction, not merely hands batching. The author did not identify the JobDef, robot type or carried quantities, so neither explanation may be chosen retrospectively. A cancellation/extra-delivery case is especially valuable: successful exact consumption can conceal untracked leftover inventory in the same route.

**F. Hidden WorkGiver is not established as the automatic cause.** HD's direct command is a FloatMenuOptionProvider that creates a job. Ordinary automatic bulk hauling upgrades a native scanner job. Registering a new automatically active WorkGiver merely to make the command discoverable would not repair A/B and could duplicate work. C424-S03 RIMMSqol and S04 Custom Alerts remain separate discovery/execution requirements; expose their supported identities through the eventual shared command boundary after investigating their actual APIs.
